## Tres mutantes sobrevivieron, uno era un hueco de anti-vacuidad real

Nueve mutantes generados contra los cinco tests existentes. Cinco murieron de
inmediato (el guard de `sealed` vacío, el booleano de `VerifyTOTP`, los dos
`Status` de respuesta hardcodeados, y saltear el `UPDATE` del secreto). Tres
sobrevivieron, y uno es un equivalente documentado — ninguno de los cuatro
pidió tocar `totp_handlers.go`, solo tests nuevos.

### Nadie mandó un body que no parsea como JSON

Sacar ese chequeo no cambiaba nada observable. El test nuevo primero enrola:
así el 400 viene demostrablemente del fallo de decode, no del chequeo de
secreto pendiente que corre después.

### La etiqueta de la URI nunca se verificó contra el email real

El label del `otpauth://` es `issuer:account`, y ningún test comprobaba que
`account` fuera el email de QUIEN llama en vez de cualquier otro string no
vacío — un mutante que hardcodeaba `"mutant@example.com"` sobrevivía sin
problema. La app autenticadora muestra ese label como nombre de la entrada:
uno equivocado mal-etiqueta en silencio a qué cuenta pertenece un código.

### El hueco real: la invalidación nunca probó que hubiera algo que invalidar

`TestTOTPEnrol_ASecondEnrolInvalidatesTheFirstRecoveryCodes` afirmaba que los
códigos del PRIMER set dejan de servir después de un SEGUNDO enrol, pero nunca
probó que sirvieran desde el principio. Un mutante que saltea persistir los
códigos de recuperación **por completo** seguía pasando el test, porque un
código que nunca fue redimible se queda trivialmente "no redimible" después
de cualquier cosa que pase después.

> Un test de invalidación sin control positivo no prueba que algo se invalidó.
> Prueba, como mucho, que nunca hubo nada que invalidar.

El arreglo: redimir un código DISTINTO del primer set inmediatamente después
del PRIMER enrol, antes de que el segundo corra. Esa redención exitosa es el
control positivo — sin él, un handler que nunca persiste nada pasa el mismo
test.

## Un mutante es EQUIVALENTE, no un hueco

Sacar el chequeo `err != nil` después de `envelope.Open()` no cambia ninguna
respuesta observable. Cada `return` de `Open()` en `envelope.go` devuelve
`secret = nil` cuando hay error, y `VerifyTOTP` ya rechaza cualquier secreto
cuya longitud no sea exactamente `TOTPSecretLength` — así que el camino sin
el chequeo llega al mismo `401` por la misma razón.

Esto no se concluyó solo porque el mutante sobrevivió: se leyó cada `return`
de `Open()` para confirmar que NINGÚN camino de error puede devolver un
secreto de la longitud correcta. No hay ningún input que distinga las dos
versiones. El chequeo se queda en el código por intención explícita y defensa
en profundidad — si el comportamiento de `VerifyTOTP` cambiara alguna vez,
este chequeo volvería a ser el único que importa. El test nuevo
(`TestTOTPVerify_ATamperedSecretIsRefusedNotCrashed`) documenta la promesa del
comentario ("la misma negativa que un código malo") sin pretender matar este
mutante puntual.
