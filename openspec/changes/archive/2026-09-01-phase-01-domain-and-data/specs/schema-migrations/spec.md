# Delta for schema-migrations

## ADDED Requirements

### Requirement: Migrations are embedded and replayed identically everywhere

The migration set SHALL be embedded in the binary as a single `fs.FS` and be the
only source of schema for every environment — the developer database, each
ephemeral test container, and the managed production database. No environment
SHALL be provisioned by a path that bypasses it.

#### Scenario: Embedded set is non-empty and well-formed

- GIVEN the embedded migration filesystem
- WHEN it is walked without a database
- THEN it contains at least one migration
- AND versions are strictly ascending integers with no gaps and no duplicates
- AND every migration declaring an `Up` section also declares a `Down` section

### Requirement: Migrations are reversible and idempotent

The full set MUST apply, reverse completely, and apply again on a fresh database
with no error and no residue.

#### Scenario: Up, down to zero, up again

- GIVEN a fresh empty PostgreSQL container
- WHEN the set is applied, then reversed to version 0, then applied again
- THEN every step succeeds
- AND after the final apply the schema is identical to the first apply — same tables, policies, grants and indexes

#### Scenario: Reversal leaves no application tables behind

- GIVEN the set has been applied and then reversed to version 0
- WHEN schema `public` is listed
- THEN no table of the data model remains, only the migration bookkeeping table

### Requirement: Roles are provisioned by migration and never dropped

Database roles SHALL be created by a migration using SQL `CREATE ROLE`, guarded on
`pg_roles` so replay is safe, with `NOSUPERUSER NOCREATEDB NOCREATEROLE NOBYPASSRLS
LOGIN`. Grants SHALL be re-applied unconditionally. A `Down` section MUST revoke
grants and MUST NOT drop a role, because a role may own objects or be in use by
another database in the same cluster.

#### Scenario: Role migration is safe to replay

- GIVEN the role migration has already run once
- WHEN it is applied again against the same cluster
- THEN it succeeds without error and the role attributes are unchanged

#### Scenario: Roles precede any policy

- GIVEN the migration set ordered by version
- WHEN the first migration that enables row level security is located
- THEN the migration creating the roles has a strictly lower version

#### Scenario: Down revokes without dropping

- GIVEN the role migration has been applied
- WHEN it is reversed
- THEN the roles still exist in `pg_roles`
- AND their grants on application objects have been revoked

### Requirement: Role passwords never appear in migration text

A role password SHALL NOT be written into any migration file. Password bootstrap
SHALL run outside the migration set, as the owner, with the value supplied as a
bind parameter and quoted server-side.

#### Scenario: No password literal in the migration set

- GIVEN the embedded migration files
- WHEN their text is scanned
- THEN no `PASSWORD` literal appears in any of them

#### Scenario: Bootstrap sets the password without interpolation

- GIVEN a bootstrap call with a password value
- WHEN it runs against the database as the owner
- THEN the role can authenticate with that value
- AND the value was passed as a bind parameter, not concatenated into SQL text

### Requirement: Generated query code is committed and verified

Generated database access code SHALL be committed to the repository and
regenerated by the project's generate target. Continuous integration MUST fail when
regeneration produces a diff, so the SQL under review is the SQL that runs.

#### Scenario: Generated code is current

- GIVEN a clean working tree
- WHEN the generate target is run
- THEN no tracked file changes

### Requirement: The integration suite cannot silently skip itself

The database-backed suite MAY skip in short mode. When the container runtime is
unreachable it MUST fail rather than skip, unless an explicit opt-out variable is
set, and it MUST fail outright if that opt-out is set while running in CI.

#### Scenario: Unreachable runtime fails the suite

- GIVEN the container runtime is unavailable and no opt-out variable is set
- WHEN the suite runs without short mode
- THEN it fails with a message naming the runtime as the cause

#### Scenario: Opt-out is refused in CI

- GIVEN the opt-out variable is set and the CI environment marker is present
- WHEN the suite starts
- THEN it fails immediately rather than skipping
