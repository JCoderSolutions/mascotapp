# Data Model Core

### Requirement: Core tenancy and identity tables exist

The schema SHALL provide `shelters`, `users`, `memberships`, `refresh_tokens` and
`media` with the columns of plan §4.1 and §4.2. Primary keys SHALL be `uuid NOT
NULL` with no database default; identifiers are time-ordered UUID v7 generated by
the application before insert. No database extension SHALL be required.

#### Scenario: Schema installs on a stock PostgreSQL

- GIVEN a fresh container running the supported PostgreSQL major version with no extensions installed
- WHEN the migration set is applied
- THEN it succeeds and `pg_extension` contains no extension added by this phase

#### Scenario: Primary keys carry no default

- GIVEN the tables of this capability
- WHEN their primary key columns are read from the catalog
- THEN each is `uuid NOT NULL` with no column default

### Requirement: Email comparison and uniqueness are case-insensitive by type

`users.email` SHALL be `citext NOT NULL UNIQUE`. The `citext` extension SHALL be
created by migration `00001`, before any table exists. Case-insensitivity SHALL be a
property of the column type, not of caller discipline: a lookup written as
`WHERE email = $1` SHALL match regardless of the casing of either side.

#### Scenario: A differently-cased lookup still finds the row

- GIVEN a user row exists with email `person@example.org`
- WHEN a query selects `WHERE email = 'PERSON@Example.ORG'` with no normalisation applied
  by the caller
- THEN the row is returned

#### Scenario: Differing case is the same user

- GIVEN a user row exists with email `person@example.org`
- WHEN a second row is inserted with `Person@Example.ORG`
- THEN the insert fails with a unique violation

### Requirement: A user belongs to many shelters; a membership belongs to one

`users` MUST NOT carry a `shelter_id`. Visibility of a `users` row to a tenant
session SHALL be derived through `memberships` scoped to the current tenant, and —
once the adoption flow exists — through an applicant relationship. `memberships`
carries `shelter_id` and follows the standard tenant policy, with
`UNIQUE (user_id, shelter_id)`.

#### Scenario: A member of the current shelter is visible

- GIVEN user U has an active membership in shelter A
- WHEN `users` is read under tenant scope A as `app_tenant`
- THEN U's row is returned

#### Scenario: A user with no relationship to the current shelter is invisible

- GIVEN user V has a membership in shelter A only
- WHEN `users` is read under tenant scope B
- THEN V's row is not returned

#### Scenario: An applicant is visible to the shelter they applied to

- GIVEN user W has no membership in shelter A but has an adoption application at shelter A
- WHEN `users` is read under tenant scope A
- THEN W's row is returned

#### Scenario: One membership per user and shelter

- GIVEN user U already has a membership in shelter A
- WHEN a second membership for the same pair is inserted
- THEN the insert fails with a unique violation

### Requirement: Media rows are tenant-scoped and logically deleted

`media` SHALL carry `shelter_id` and a nullable `deleted_at`. Logical deletion
SHALL be used where the model declares `deleted_at`; rows are not physically
removed by application paths.

#### Scenario: Media is subject to the standard isolation rule

- GIVEN a media row owned by shelter A
- WHEN the A/B isolation case is run against `media`
- THEN it passes as specified in the tenant-isolation capability
